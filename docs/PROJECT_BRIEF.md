# EduBridge AI 项目开发说明与十五天执行计划

版本：1.0  
编制日期：2026年11月16日  
开发周期：2026年11月16日至11月30日（北京时间）  
阅读对象：项目负责人与 Qoder 开发助手  
用途：理解业务流程、统一开发边界、逐日指挥 Qoder、验收参赛作品。本文为执行方案，列出的代码、部署、模型测试和指标均须实际完成后才能记为成果。

## 1 项目定位与核心决策

EduBridge AI 面向高一数学学生和辅导老师，将老师已经批改的试卷转化为有证据的错因假设、针对性诊断题、经审核的讲解和复测记录。第一版覆盖集合、函数、基本不等式。

我们要回答的不是只有“这道题怎么做”，而是“学生在哪一步出错、依据是什么、还需要做哪道题验证、讲解后能否独立解决相近问题”。这是产品的主要价值，也是参赛演示应突出展示的部分。

既定输入方案：试卷原卷图片、老师已批改且手写清晰的答题卡、AI 识别后的人工确认。老师的批改结果是原始依据，AI 不负责重新判定整张原卷的分数；AI 若发现批改与解答疑似矛盾，只提示人工复核。老师参考答案或评分说明为可选补充材料。没有参考答案时，模型生成的解答必须标为候选解答，并接受审核。

开发使用 Qoder；站点通过 Qoder Sites 发布。Qoder 是开发工具与平台，不把“Qoder 大模型”写成不存在的独立推理 API。应用内部模型通过正式 API 接入，或在经过验证后使用平台的 Cloud Agents 能力。Qoder 会员额度、应用模型费用、站点运行额度分别核对。

### 1.1 十五天的完成目标

实现一条可公开访问、可重复验证的真实流程：上传脱敏试卷和答题卡 → 人工确认题目与学生作答 → 错因假设及证据 → 学生完成诊断题 → 错因更新 → 审核后的讲解 → 新题复测 → 学习报告与打印。

计划按每天约4至6小时的集中投入、配合 Qoder 辅助开发估算，属于工程排期而非效果保证。如实际只有2至3小时，先保留核心流程，将通用视频生成、班级管理等后移，不压缩正确性和部署验收。

## 2 业务流程与交互页面

### 2.1 上传与人工确认

1. 用户选择年级和章节，创建一次学习任务，使用匿名学生代号。
2. 分别上传原卷与答题卡，支持多张图片及预览。第一版限定 JPEG、PNG、WebP；单文件不超过10MB、每次不超过10张，这是项目初始限制，需同时满足平台限制。
3. 视觉模型提取题干、公式、题号、学生作答步骤、老师批改标记以及无法识别的区域。原图与结构化内容并排展示。
4. 用户逐题确认或编辑，选中老师已判错的题目。不确定的字符显示“待确认”；不由模型补写看不清的条件。空白作答、漏页、题号错配单独标记。
5. 仅在相应题目确认后允许诊断。确认修改生成新版本，旧诊断自动过期，需要重算。

第一版允许人工补录关键题目，保证遇到识别不清时仍能继续学习。人工补录必须在记录中注明来源，不能计入自动识别准确率。

### 2.2 诊断与针对性练习

对每道已确认错题，先给出章节、相关知识点、首个可定位的错误步骤、相关条件以及1至3个错因假设。错因类别包括概念混淆、条件遗漏、定义域遗漏、分类不全、运算失误、推理缺失和证据不足。

根据同一份错答可能有多种解释的事实，模型不能只凭最终答案判定“学生粗心”或“概念不懂”。需要设计1至2道短诊断题，区分不同假设。学生答题后，诊断引擎更新为“得到支持”“未得到支持”“仍需验证”，保存依据。模型自报置信度不是经过校准的概率，不显示为精确百分比。

### 2.3 教学与复测

教学模型生成短讲解：指出学生原步骤 → 解释被遗漏条件或错误规则 → 展示正确做法 → 给一个检查方法。审核通过后才显示给学生。文字讲解为必做；视频讲解后置。

讲解后发放另一道同知识点的新题作为复测。完成一道复测只能记录“本次通过”或“仍需练习”，不能宣称已长期掌握，更不能虚构提分效果。报告同时展示原错题、诊断题结果、教学记录和复测结果。

## 3 用一个案例理解完整流程

案例属于人工设计的演示样例，不是已采集的真实学生结果。

题目：正数 x 的取值满足题目约束，求含 x 与倒数项的表达式最小值。学生使用基本不等式写出下界，却没有检查等号对应的 x 是否落在允许范围。

原始证据必须分别定位“题目中的变量范围”和“学生写出等号成立条件的步骤”。AI 提出“忽略等号可取得性”的假设，而不是只说“不会基本不等式”。

诊断题A：给出一个等号条件可达到的简单情形，要求写出等号成立时的变量值。诊断题B：保留类似表达式但修改变量范围，使等号点不在允许范围，要求判断原下界是否可作为最小值。两题区分“不会求等号条件”与“求出了但未检查范围”。

审核需要检查下界、端点和取值范围。只有定义域内确实可达到时，才能称为最小值；只能逼近时，要区分下确界与最小值。SymPy 在支持范围内验证代数与不等式步骤，教学模型解释规则适用条件。

用户学完后完成不同数值的新题，报告描述本次复测结果。案例中的具体表达式由开发时固定样例和人工参考解答给出，避免未审核公式直接流入演示。

## 4 技术栈与部署决策

### 4.1 默认技术方案

采用“React 前端 + Sites 服务端能力 + 可独立部署的 Python 数学验证服务”。优先复用 Sites 已支持的数据库、文件存储与服务端函数；不先租一整台服务器。数学验证若不能在平台运行，就部署一个范围明确的 Python 服务。

| 层级 | 拟用技术 | 用途与选择理由 |
|---|---|---|
| 前端 | React、TypeScript、Vite | 页面、表单、任务状态与组件化开发 |
| 样式 | Tailwind CSS 或项目现有样式方案 | 统一界面，初期不混用多个UI体系 |
| 数学显示 | KaTeX | 正确显示题干、公式与讲解，公式与业务字段分离 |
| 输入校验 | Zod，Python侧Pydantic | 验证模型JSON、API输入、字段范围 |
| 站点与轻后端 | Qoder Sites、平台支持的 Server Functions | 发布网页、代理模型请求、保存任务状态 |
| 数据 | Sites 平台数据库与私有对象存储 | 保存结构化记录和原图，不把正式数据只存浏览器 |
| 数学服务 | Python 3.11或3.12、FastAPI、Uvicorn、SymPy | 提供受约束的数学验证接口；部署到支持Python的环境 |
| HTTP调用 | 服务端 fetch，Python侧HTTPX | 正式模型API及数学服务调用 |
| 工作流 | 显式状态机与任务记录 | 十五天内优先保证可恢复、可审核，不先引入复杂框架 |
| 工程质量 | Git、Vitest、Playwright、pytest | 版本记录、状态规则与核心链路验证 |

版本通过实际环境和官方兼容性确认后锁定，不让 Qoder 无条件升级全部依赖。LangGraph 不作为第一版必须依赖；只有需要复杂持久化图编排、且收益明确时才引入。

### 4.2 第一天必须验证的能力

Qoder 检查当前客户端、账号版本与 Sites 功能是否可用，并用小样验证：页面发布、服务端函数、Secret、数据库写读、文件上传、对外HTTPS调用，以及执行时长和请求大小限制。某一项“文档支持”不能替代当前账号的实际测试。

如果平台只支持静态站点或服务端限制无法满足业务，启用备选方案：Sites 托管 React 前端，外部 FastAPI 承担业务API与数学工具，初期SQLite加SQLAlchemy。SQLite 仅适合单实例持久磁盘和低并发演示；多实例或无持久磁盘时改用托管 PostgreSQL，不把本地临时文件当正式数据库。

默认方案和备选方案二选一，不同时搭两套完整后端。第一天记录选择依据；第二天结束前确定。外部服务必须可从公网通过HTTPS访问；发布站点不能调用开发者本机 localhost。

### 4.3 你需要理解的三个区别

Qoder 帮我们编程；Sites 托管网站及支持的服务端功能；模型 API 为应用提供识别、分析与生成能力。三者各有额度和限制。

普通云服务器能让我们自行安装环境，但需要维护。Sites 减少维护工作，代价是必须遵守平台的运行环境和资源限制。不能因它有 Server Functions 就推断能直接运行常驻 FastAPI、FFmpeg 或任意 Python 包。

## 5 大模型接入与角色分工

### 5.1 首轮候选模型

以下是2026年11月16日按官方公开文档选择的候选，不代表当前账号已开通。模型ID、可用地域、价格、结构化输出方式及用券资格须在接入前再次确认。

| 角色 | 首选候选 | 输入输出 | 需要验证 |
|---|---|---|---|
| 试卷与手写识别 | 百炼 qwen3.6-plus | 原卷和答题卡图片 → 结构化题目与步骤 | 手写公式、题号对应、无法识别时是否保留不确定项 |
| 错因诊断与出题 | 百炼 qwen3.6-plus | 已确认题目、作答、知识规则 → 错因假设与诊断题 | 有证据、不跳步、题目只针对目标错因 |
| 教学讲解 | 百炼 qwen3.6-plus | 确认后的错因、诊断表现、审核反馈 → 教学脚本 | 适合高一水平，保持公式和条件准确 |
| 独立审核 | 百炼 deepseek-v4-pro | 原题、作答、规则、待审内容及工具结果 → 审核结论 | 当前账号可用性、延迟、题解与适用条件审查能力 |
| 审核备选 | 百炼 deepseek-v4-flash | 同上 | 通过固定样例后再用于演示，不预设其效果优于其他模型 |

选择不同模型家族做教学与审核，可以减少完全相同生成路径的重复，但不是数学正确性的保证。审核应尽量先依据原题独立求解，再与候选讲解比较；不要求模型返回隐藏思维链，只返回可核对的步骤、证据和结论。

模型候选的效果须用固定样例评测后决定。不要为了“多模型”额外串接四五家供应商。首版可统一从百炼调用两个家族，降低账号和接口复杂度。若第二模型未开通，只能展示“单模型复核模式”，不得冒充已完成多模型审核；P0 多模型验收仍算未完成。

### 5.2 API接入要求

服务端维护 ModelProvider 适配层，方法至少包含 recognize、diagnose、generateQuestions、teach、review。业务层不直接拼接供应商细节，便于后续更换模型。

配置项：MODEL_BASE_URL、MODEL_API_KEY、VISION_MODEL、DIAGNOSIS_MODEL、TUTOR_MODEL、REVIEW_MODEL、MATH_VERIFY_URL、MATH_VERIFY_TOKEN。Base URL 从当前地域和业务空间的官方控制台复制，不硬编码旧地址。模型能力不同，不强行给每个模型发送相同的思考参数、temperature或JSON模式参数。

密钥只能进入服务端环境变量或平台Secret。浏览器代码、VITE_开头变量、Git提交、日志、截图中均不能出现真实密钥。调用通过本项目服务端完成，前端不直连供应商。

第一天先验证一条最小文本请求；第二天验证图片请求和两个模型可用性。无密钥时可开发带明显“模拟数据”标识的界面，但真实连通项必须保持未完成状态，不虚构调用成功。

### 5.3 返回结构与费用记录

每次模型返回先校验结构，不符合schema则进行一次格式修复；仍失败就返回可重试错误，不用空对象假装成功。记录模型实际ID、供应商请求ID、耗时、输入输出用量、重试次数、schema版本和提示词版本。

费用按实际用量和当时单价估算，账单数据为最终依据。用券是否抵扣与模型能否被调用是两回事。学生券不能默认覆盖所有模型，尤其注意三方模型、部分OCR、全模态、语音、视频及已有活动折扣的账单。Coding Plan、Token Plan不能直接当成项目后台模型额度。

先用少量脱敏样例测通并检查账单，再扩大调用。应用端设置每次任务最多3道错题、单题最多2道诊断题、一次审核修改循环、每个任务模型调用上限12次的初始预算规则；它们是工程限额，可按实测调整，不是平台默认保证。

## 6 多模型编排与发布门槛

采用可持久化的步骤状态，而不是让一个长提示词一次完成所有功能。

1. Recognize：视觉识别保存草稿。
2. Confirm：用户修订题干、学生作答与判错标记，生成 confirmed_version。
3. Diagnose：教学模型提出错因假设、证据和候选诊断题。
4. Validate：执行schema校验、知识规则检查；适用的数学表达式发送SymPy服务。
5. Review：审核模型依据原题和工具结果独立核查诊断题与参考答案。
6. Revise：不通过时按具体反馈修改一次，再验证、再审核；仍不通过则 needs_review。
7. Answer：发布通过审核的诊断题，学生提交作答；更新错因假设。
8. Teach：生成并审核教学说明。
9. Retest：生成、验证并审核不同的复测题，学生完成后形成报告。

每项诊断题、讲解和复测题都有自己的 artifact_version、review_status 和 verification_status。内容修改后，旧审核不继承。只有针对当前版本的审核通过才能发布。

### 6.1 状态机

任务状态：draft → uploaded → recognizing → awaiting_confirmation → confirmed → diagnosing → diagnostic_ready → diagnostic_submitted → teaching_ready → retest_ready → completed。

任何阶段可进入 failed 或 needs_review；任务执行和内容审核分别记录，避免“任务执行成功”被误解为“数学正确”。只有当前步骤的前置条件满足时才可前进。重试使用幂等键，避免重复创建题目或重复付费调用。

### 6.2 审核字段

review_status 为 pass、revise、needs_human_review。issues 至少含问题类型、严重程度、对应字段或步骤、证据和修改建议。

verification_status 为 passed、failed、unsupported、timeout。unsupported 和 timeout 都不等于验证通过。对必需数学验证的题型，无法验证则转人工复核；人工复核通过也只能标为“人工审核通过”，不能显示“SymPy验证通过”。

审核模型超时或供应商不可用时，保留用户输入和未发布草稿，提示重试。不能绕过审核直接显示未经检查的生成内容。

## 7 数学验证和知识证据

### 7.1 第一版验证范围

支持有限集合运算、简单实数域方程、定义域约束下的代数等价、部分单变量多项式或有理不等式，以及带明确正性条件和等号条件的基本不等式模板。

SymPy验证的是受支持的数学命题，不验证学生认知、不理解所有自然语言证明，也不保证生成题目的教学质量。数值抽样只能用于发现反例，不能作为“已证明恒成立”的依据。

接收结构化表达式树与明确的变量、实数域、区间、非零约束、待验证关系。不直接对用户或模型任意字符串运行 eval、exec，也不把不可信字符串直接交给 parse_expr 或 sympify。用允许的运算节点构造SymPy对象，限制节点数、指数、变量数和执行时间，超时终止隔离进程。

### 7.2 知识规则库

首版用人工编写并核查的JSON/YAML规则库，不先搭大型向量数据库。每条规则含 rule_id、章节、规则陈述、适用条件、常见误用、人工参考来源和规则版本。

例如基本不等式需区分正性条件和等号可取得性；函数问题需检查定义域与分母非零；集合问题需区分元素属于与集合包含。引用教材时记录书名、版次和实际核对的章节或页码，未核对的页码不能编造。

模型诊断必须引用 rule_id，并关联学生具体step_id以及题目条件。RAG作为后续扩展：资料变多且检索确有必要时再引入切块、嵌入模型和向量检索，并保留来源。

## 8 核心数据结构

所有业务记录包含 id、owner_id或受保护的匿名会话标识、created_at、updated_at。时间以UTC存储，界面按北京时间展示。使用外键或等效关联、必要索引与迁移脚本。

| 记录 | 关键字段 | 关系 |
|---|---|---|
| learning_tasks | student_alias、grade、chapter、status、confirmed_version、mode | 一次完整学习流程 |
| assets | task_id、kind、object_key、mime、size、sha256、page_index | 原卷、答题卡与可选参考答案 |
| questions | task_id、number、stem、latex、conditions、teacher_result、version | 关联原图及确认版本 |
| answer_steps | question_id、step_index、content、source_page、bbox | 关联可定位的学生步骤 |
| confirmations | task_id、version、confirmed_fields、confirmed_at | 记录人工修改与确认 |
| diagnoses | question_id、version、first_error_step_id、hypotheses、evidence、rule_ids | 错因假设及后续支持状态 |
| generated_items | diagnosis_id、purpose、stem、answer_private、rubric_private、artifact_version | purpose区分诊断题和复测题 |
| attempts | item_id、student_response、grading_result、evidence | 学生作答和复测结果 |
| teaching_contents | diagnosis_id、text、script、video_object_key、artifact_version | 已审核教学及可选视频 |
| checks | artifact_id、artifact_version、check_type、status、issues、model_run_id | 模型审核、规则与SymPy结果 |
| model_runs | task_id、role、actual_model_id、request_id、usage、latency、status | 调用追踪与费用估算 |
| jobs | task_id、stage、idempotency_key、status、attempts、error_code | 可恢复执行与重复请求控制 |

evidence字段至少包含 source_type、asset_id或question_id、step_id、snippet、bbox或位置说明。bbox由识别结果给出时只是定位建议，界面允许人工调整；模型不能虚构精确像素证据。

答案与评分规则不能与学生未作答题目一起返回。前端隐藏不等于安全，必须由服务端按作答阶段过滤字段。

## 9 最小 API 合同

这是前后端约定，URL可由平台路由实现，不能理解为Sites已自动创建这些接口。返回统一包含 data、error、request_id；异步任务返回202与job_id，前端轮询任务状态。HTTP错误码区分参数、权限、冲突、限流和上游故障。

| 接口 | 作用 | 关键校验 |
|---|---|---|
| GET /api/health | 服务存活与构建版本 | 不泄露密钥或内部配置 |
| POST /api/tasks | 创建学习任务 | 匿名代号、年级、章节 |
| POST /api/tasks/{id}/assets | 上传或申请受控上传 | 文件真实类型、大小、归属 |
| POST /api/tasks/{id}/recognize | 启动识别 | 材料完整、幂等键 |
| GET /api/jobs/{id} | 获取执行进度 | 只能读取本人任务 |
| PATCH /api/tasks/{id}/confirmation | 保存确认内容 | 版本冲突检测；修改使旧结果失效 |
| POST /api/tasks/{id}/diagnose | 生成错因及诊断题 | 已确认版本、题量与调用预算 |
| POST /api/items/{id}/attempts | 提交诊断或复测作答 | 不接受客户端传入“正确答案” |
| POST /api/diagnoses/{id}/teach | 生成并审核教学 | 有学生诊断表现或显式跳过记录 |
| POST /api/diagnoses/{id}/retest | 创建审核后的复测题 | 教学内容已发布 |
| GET /api/tasks/{id}/report | 读取学习报告 | 正确区分未完成与不通过 |
| GET /api/tasks/{id}/print | 获取打印所需数据 | 题目与答案分离，所有权校验 |
| DELETE /api/tasks/{id} | 删除任务与附件 | 关联数据清理并可报告部分失败 |
| POST /internal/math/verify | 数学工具校验 | 服务间鉴权、受限AST、超时 |

若Sites函数执行时长不足以容纳模型任务，不能在HTTP返回后假设后台代码还会继续。必须验证平台支持的持久化任务或Cloud Agents执行方式；不支持时使用外部任务进程和数据库jobs。不得用纯内存队列承诺重启恢复。

## 13 评测方法与验收标准

首轮构建18道人工核查的脱敏或自行设计案例：三章节各6道。建议12道用于提示词和流程调试，6道作为冻结的回归检查；样本小，只能描述本次测试表现，不外推成产品总体准确率。

每题准备原题、学生作答、老师标记、人工正确解、预期错误步骤、可接受的错因解释、支持或反驳假设的诊断题和参考答案。公开使用前核对材料使用权，避免发布整张有版权限制的试卷。

| 指标 | 计算与记录 | 初期验收目标 |
|---|---|---|
| 流程完成率 | 完整走到报告的测试任务数／测试任务总数 | 冻结的6例均能完成，失败有原因 |
| 证据可定位率 | 可定位到实际题目条件或步骤的证据项／所有证据项 | 冻结集全部人工核对，不接受虚构来源 |
| 题目与答案正确性 | 人工核查生成题目条件、答案及解释 | 展示题目全部人工抽检或审核，不发布已知错误 |
| 审核阻断 | 给定人工植入的错误，是否阻止发布 | 定义域遗漏、等号不可达、错答案三类均覆盖 |
| 未审核泄露 | 故意让审核超时、不通过、版本过期 | 均不能自动发布 |
| 真实识别质量 | 人工修正前正确的关键字段数／关键字段总数 | 如实报告原始结果，人工修正另记 |
| 任务耗时与费用 | 分阶段实际耗时、usage、估算费用与账单核对 | 先测后设目标，不预填优秀数字 |
| 数据隔离与恢复 | 两个独立会话交叉读取、重启、刷新、重试 | 不串数据、不泄露答案、重复调用可控 |

必须保留至少一个模型无法识别、一个数学工具不支持、一个审核不通过的案例。展示系统如何诚实处理失败，比隐藏错误更有工程价值。

## 14 数据保护与成本控制

公开演示只用脱敏或自行制作的样例。真实材料保存在受保护空间，访问原图需授权或短时链接；匿名会话的标识必须不可预测，由服务端校验，不能把task_id本身当权限。

上传图片和OCR文本视为用户数据，不作为系统指令执行。对模型提示注入和恶意文件设置输入约束；输出文字渲染避免未经净化的HTML，公式渲染也采用安全配置。

执行删除时同时处理附件与结构化记录。默认保留周期可设7天作为第一版产品设置，并在界面说明；仅在实现删除任务或定期清理后才能承诺自动删除。

成本设置应用端题量、频率、调用次数与输出长度限制；开启供应商预算控制并确认它是告警还是可停止调用的硬限制。公开演示增加频率限制和并发限制，不开放无限上传无限生成。日志不记录密钥，不默认记录完整真实学生原图。

若300元券实际抵扣Qoder月卡59元，则理论剩余241元，实际以卡券余额为准。预算建议先保留50至80元用于小规模模型测试，其他余额等待部署验证后再安排；这是内部预算而非模型报价或抵扣承诺。

## 15 视频和后续扩展

视频讲解分两层：第一层为已审核脚本驱动的模板画面、字幕与可选旁白，先预生成一个固定案例；第二层才是任意题的实时生成。第一层便于校验公式、控制时长和避免数学文字失真，更适合本次排期。

FFmpeg只负责合成，不是大模型。语音服务和视频生成服务可能有独立费用及用券限制，未经核对不购买。即便视频由AI参与制作，所有公式、条件、例题答案和配音文本仍需审核，不能用生成视频替代文字正确性检查。

后续扩展包括班级视图、多学生长期学情、更多章节、教材检索、复杂证明审查、异步任务调度和更大评测集。以上不影响本期P0闭环交付。

## 17 给 Qoder 的完成定义

代码存在不等于功能完成；本机预览不等于公网可用；模型返回不等于审核通过；人工修改后正确不等于自动识别正确；一题复测通过不等于长期掌握。

只有在目标环境中运行、有可复核输入输出、满足当前版本的确认与审核要求、异常不误导用户，才能把对应任务标记为完成。每天只推进已经选定的最小范围，并把实际结果和下一步清楚交给项目负责人。
